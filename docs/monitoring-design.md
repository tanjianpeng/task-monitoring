# 数据大屏跑批监控设计方案

## 1. 需求理解

本方案用于支撑数据大屏展示不同系统下不同跑批任务的运行状态，满足以下目标：

1. 各业务系统通过统一接口上报任务开始、结束、失败、进度等状态。
2. 平台将上报数据落库，形成任务主数据、任务实例、状态事件、依赖关系、页面布局等数据。
3. 大屏可实时查询某一日任务运行情况，并按待执行、执行中、成功、失败、延迟等状态展示。
4. 支持甲方设计图中的字段，如所属系统、负责人、监督人、预计开始时间、最晚开始时间、历史平均耗时、当前耗时、预计结束时间、开始时间、结束时间等。
5. 支持后续扩展更多系统、更多任务、更多展示页面，而不需要反复改表。

## 2. 设计原则

1. 主数据和运行数据分离。
2. 任务定义和任务实例分离。
3. 状态以“当前快照 + 事件流水”双模型保存。
4. 展示配置和业务数据分离。
5. 接口统一，调用系统只需要按任务编码上报。

## 3. 核心业务模型

### 3.1 主体对象

1. 系统
2. 任务定义
3. 任务依赖关系
4. 任务页面坐标和展示配置
5. 每日任务实例
6. 任务状态事件流水
7. 任务耗时统计

### 3.2 主数据与运行数据关系

1. `monitor_system` 维护系统信息。
2. `monitor_task` 维护任务定义。
3. `monitor_task_dependency` 维护任务前置依赖。
4. `monitor_task` 在维护任务定义的同时，承载任务展示相关配置。
5. `monitor_task_instance` 按“业务日期 + 任务”生成每日运行实例。
6. `monitor_task_event` 保存外部系统每次回调的原始事件。
7. `monitor_task_stat_daily` 保存统计结果，支撑历史平均耗时。

## 4. 状态设计

### 4.1 统一状态枚举

建议统一为以下状态：

1. `PENDING` 待执行
2. `RUNNING` 执行中
3. `SUCCESS` 成功
4. `FAILED` 失败
5. `DELAYED` 延迟未开始
6. `TIMEOUT` 超时未结束
7. `CANCELLED` 已取消

### 4.2 状态判定规则

结合设计图和备注，建议按以下逻辑计算：

1. 初始状态：到预计开始时间前为 `PENDING`。
2. 正常启动：收到开始时间后变更为 `RUNNING`。
3. 延迟启动：当前时间大于最晚开始时间，仍未收到开始时间，则为 `DELAYED`。
4. 成功完成：收到结束时间且状态为成功，则为 `SUCCESS`。
5. 执行失败：收到结束时间且状态为失败，则为 `FAILED`。
6. 运行超时：已收到开始时间，但当前时间大于预计结束时间且未结束，则为 `TIMEOUT`。
7. 人工取消：业务明确取消时为 `CANCELLED`。

### 4.3 设计图字段映射

1. 预计开始时间：任务定义导入或人工维护。
2. 最晚开始时间：预计开始时间 + 容忍延迟分钟数。
3. 开始时间：业务系统回调。
4. 结束时间：业务系统回调。
5. 当前耗时：当前时间 - 开始时间。
6. 历史平均耗时：优先取近 30 天同任务平均值，月末任务可取近 N 次月末平均值。
7. 预计结束时间：开始时间 + 历史平均耗时；未开始时可用预计开始时间 + 历史平均耗时。

## 5. 库表设计

### 5.1 `monitor_system` 系统表

用途：
维护被监控系统基础信息。

关键字段：

1. 系统编码
2. 系统名称
3. 系统负责人
4. 监督人
5. 系统类型
6. 是否启用

### 5.2 `monitor_task` 任务定义表

用途：
维护任务静态信息，是所有实例生成的基础。

关键字段：

1. 任务编码
2. 任务名称
3. 所属系统编码
4. 负责人
5. 监督人
6. 计划开始时间
7. 计划结束时间
8. 容忍延迟分钟
9. 是否月末任务
10. 是否需要展示
11. 是否自动生成实例
12. 页面编码
13. 分组编码

### 5.3 `monitor_task_dependency` 任务依赖表

用途：
维护任务依赖关系，既可以用于时序图，也可以用于状态联动和链路展示。

关键字段：

1. 当前任务编码
2. 前置系统编码
3. 前置任务编码
4. 前置任务名称
5. 依赖类型
6. 是否强依赖
7. 依赖产物说明

### 5.4 `monitor_task_instance` 任务实例表

用途：
保存每天每个任务的运行快照，是大屏展示的核心表。

关键字段：

1. 业务日期
2. 任务编码
3. 系统编码
4. 当前状态
5. 计划开始时间
6. 最晚开始时间
7. 计划结束时间
8. 实际开始时间
9. 实际结束时间
10. 当前耗时秒数
11. 历史平均耗时秒数
12. 预计结束时间
13. 是否超时
14. 是否延迟
15. 失败原因
16. 最近回调时间
17. 数据源系统
18. 扩展报文

### 5.5 `monitor_task_event` 任务事件流水表

用途：
保存每次接口调用的原始事件，便于审计、排错、重放。

关键字段：

1. 请求流水号
2. 业务日期
3. 任务编码
4. 事件类型
5. 事件时间
6. 上报系统
7. 上报状态
8. 原始请求报文
9. 处理结果
10. 入库时间

### 5.6 `monitor_task_stat_daily` 任务统计表

用途：
沉淀历史统计值，支撑平均耗时、成功率、月末任务平均耗时等。

关键字段：

1. 业务日期
2. 任务编码
3. 系统编码
4. 是否成功
5. 实际耗时秒数
6. 是否月末
7. 是否延迟启动
8. 是否超时结束

## 6. 实例生成机制

建议每日由调度程序在凌晨或白天初始化当天实例：

1. 读取启用中的任务定义。
2. 按业务日期生成 `monitor_task_instance`。
3. 将计划开始时间、计划结束时间、最晚开始时间、历史平均耗时写入实例。
4. 初始状态设置为 `PENDING`。

这样做的好处是：

1. 大屏可以在任务尚未开始前就展示完整卡片。
2. 业务系统只需要上报状态，不需要先创建任务。

## 7. 通用接口设计

### 7.1 设计目标

统一接口只做两件事：

1. 接收外部系统任务状态回传。
2. 提供大屏和管理端查询。

### 7.2 外部系统上报接口

建议提供一个统一入参接口：

`POST /api/monitor/task/{params}`

其中：

1. `begin` 表示开始
2. `end` 表示结束

请求核心字段：

1. 系统编码 `systemCode`
2. 任务编码 `taskCode`
3. 业务日期 `bizDate`
4. 运行批次 `runNo`
5. 开始时间 `startTime`
6. 结束时间 `endTime`
7. 执行状态 `resultStatus`
8. 错误信息 `errorMessage`
9. 耗时分钟数 `costMinutes`
10. 操作人 `operator`
11. 备注 `remark`
12. 扩展信息 `ext`

### 7.3 幂等设计

必须支持幂等，避免业务系统重复回调造成脏数据：

1. 业务方传 `requestId`
2. 平台按 `requestId + taskCode + bizDate` 做唯一约束
3. 重复报文直接返回成功

### 7.4 大屏查询接口

建议至少提供以下接口：

1. `GET /api/monitor/dashboard/summary`
2. `GET /api/monitor/dashboard/tasks`
3. `GET /api/monitor/dashboard/links`
4. `GET /api/monitor/task/detail`

说明：

1. `summary` 返回系统数、任务总数、待执行、执行中、成功、失败、延迟等统计。
2. `tasks` 返回任务卡片列表。
3. `links` 返回任务依赖关系和连线信息。
4. `detail` 返回任务详情和事件流水。

## 8. 推荐处理流程

### 8.1 外部系统回调流程

1. 接收请求并校验签名。
2. 校验系统编码、任务编码是否存在。
3. 记录 `monitor_task_event` 事件流水。
4. 按动作类型更新 `monitor_task_instance`。
5. 必要时回写统计表。
6. 返回标准结果。

### 8.2 大屏读取流程

1. 查询统计汇总。
2. 查询页面布局。
3. 查询实例快照。
4. 前端按布局坐标渲染任务卡片和连线。

## 9. 关键计算口径

### 9.1 历史平均耗时

建议口径：

1. 平日任务：取近 30 个自然日成功实例平均耗时。
2. 月末任务：取近 6 次月末成功实例平均耗时。
3. 历史样本不足时：取任务定义中的默认耗时。

### 9.2 最晚开始时间

计算方式：

`最晚开始时间 = 计划开始时间 + 容忍延迟分钟`

### 9.3 预计结束时间

计算方式：

1. 已开始未结束：`实际开始时间 + 历史平均耗时`
2. 未开始：`计划开始时间 + 历史平均耗时`

## 10. 实施建议

### 10.1 第一期建议范围

第一期先做最小可用闭环：

1. 系统表
2. 任务定义表
3. 依赖表
4. 布局表
5. 任务实例表
6. 事件流水表
7. 上报接口
8. 大屏查询接口

### 10.2 第二期扩展

1. 任务告警
2. 短信或邮件通知
3. WebSocket 实时推送
4. 任务拓扑自动布局
5. SLA 统计分析

## 11. 风险与注意事项

1. 不同系统时间来源不一致，建议统一校验并记录服务器接收时间。
2. 部分系统无法精确回传开始时间时，需支持只回传状态。
3. 一个任务可能有多条依赖关系，因此依赖表必须独立设计，不能塞在任务表里。
4. 大屏坐标和业务表分离，避免前端布局变更影响核心数据。
5. 同一任务一天可能重复执行，当前实例表已使用 `run_times` 表示重跑次数。

## 12. 推荐结论

推荐采用“6 张核心表 + 1 张统计表 + 1 套统一上报接口 + 1 套大屏查询接口”的方案。这样既能覆盖当前甲方的大屏展示需求，也能支持后续新增系统、任务、依赖链和状态规则。
