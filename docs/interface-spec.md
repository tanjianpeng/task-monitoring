# 跑批监控接口规范

## 1. 接口总览

本期建议收敛为 2 类核心接口：

1. 本地查询接口
2. 统一任务动作上报接口

其中：

1. 前端每 1 分钟调用一次本地查询接口。
2. 各业务系统统一调用一个上报接口，通过 `status` 区分 `start`、`end`、`restart`、`fail`。
3. `end` 表示成功结束，`fail` 表示失败结束。
4. 支持业务系统重跑时调用 `restart`。
5. 日志记录只放在统一动作上报接口上，本地查询接口不记录调用日志。

## 2. 接口清单

### 2.1 本地查询接口

- 本地查询接口已拆分为 3 个接口：
  `GET /api/monitor/local/queryStatistics`
  `GET /api/monitor/local/querySystems`
  `GET /api/monitor/local/queryTaskStatus`
- 调用方：前端大屏
- 调用频率：每 1 分钟一次
- 接口说明：从本地数据库查询当天任务运行情况，并在查询时实时计算任务状态
- 三个本地查询接口的业务日期都由后端优先取实例表最新一条业务日期，实例表为空时回退到昨天日期
- `querySystems` 预留 `systemName` 模糊查询入参，返回系统维度的待执行、执行中、成功、失败和总数

状态计算建议：

1. `NOTSTART`：未开始，当前还没有收到开始时间回传
2. `RUNNING`：已收到开始时间，且开始时间未超过最晚开始时间，未收到结束时间
3. `DELAYED`：已收到开始时间，但开始时间超过最晚开始时间
4. `DELAYED`：已开始未结束，且当前时间已超过预计结束时间
5. `SUCCESS`：已收到结束时间，结束结果为成功；若实际结束时间超过预计结束时间，同时标记为延迟
6. `FAILED`：已收到结束时间，结束结果为失败；若实际结束时间超过预计结束时间，同时标记为延迟

### 2.2 统一任务动作上报接口

- 接口名称：统一任务动作上报
- 请求方式：`POST`
- 接口路径：`/api/monitor/task/report`
- 调用方：各业务系统
- 接口说明：任务开始、成功结束、失败结束、重跑开始都通过同一个接口调用，通过报文里的 `status` 区分动作

状态字段说明：

1. `start`：任务开始
2. `end`：任务成功结束
3. `restart`：任务重跑开始
4. `fail`：任务失败结束

#### 2.2.1 `start` / `restart` 开始类动作

处理动作：

1. 校验系统编码和任务编码
2. 验签
3. 写入调用日志
4. 更新任务实例开始时间
5. 按开始时间与最晚开始时间比较，更新任务当前状态为 `RUNNING` 或 `DELAYED`
6. 计算预计结束时间

#### 2.2.2 `end` / `fail` 结束类动作

处理动作：

1. 校验系统编码和任务编码
2. 验签
3. 写入调用日志
4. 更新任务实例结束时间
5. 更新执行结果状态
6. 计算实际耗时
7. `end` 调用则更新为 `SUCCESS`
8. `fail` 调用则更新为 `FAILED`

## 3. 日志记录建议

建议只在调用类接口中记录日志，不在查询接口中记录：

1. 新增 `monitor_task_log` 日志表
2. `start`、`restart` 调用时记录一条开始类日志
3. `end`、`fail` 调用时记录一条结束类日志

日志建议字段：

1. 请求流水号
2. 调用URL
3. 系统编码
4. 任务编码
5. 业务日期
6. 接口类型
7. 请求报文
8. 返回结果
9. 调用时间

## 4. 返回规范

建议所有接口统一返回 `ResultDto<T>` 结构：

```json
{
  "code": "0000",
  "message": "success",
  "data": {}
}
```

其中：

1. `0000` 表示成功
2. 非 `0000` 表示失败
3. 失败时返回明确错误信息，方便业务系统定位问题
